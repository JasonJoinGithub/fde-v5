# W7 · 第 7 周：加 AI，但要有边界

## Day 43 · 第一次调用大模型 API

**你要先搞清楚一件事**：调 API 不是"让 AI 帮你想"，是**让 AI 完成一个明确定义的任务**。

**任务**：

1. 选一家你能访问的模型 API（DeepSeek / 通义 / 智谱 / OpenAI，任选）
2. 拿到 API Key，**存到环境变量里，不要写进代码**：

```bash
export MY_LLM_KEY="sk-xxxxxx"
```

3. 写 `subtitle_qc/translate.py`，实现一个最小调用：

```python
import os
import json
from urllib import request, error

API_URL = "https://api.deepseek.com/chat/completions"   # 按你选的厂商改
API_KEY = os.environ.get("MY_LLM_KEY")


def call_llm(messages, model="deepseek-chat"):
    if not API_KEY:
        raise RuntimeError("没有设置 MY_LLM_KEY 环境变量")

    body = json.dumps({
        "model": model,
        "messages": messages,
        "temperature": 0.2,
    }).encode("utf-8")

    req = request.Request(
        API_URL,
        data=body,
        headers={
            "Content-Type": "application/json",
            "Authorization": "Bearer " + API_KEY,
        },
    )

    try:
        with request.urlopen(req, timeout=60) as resp:
            data = json.loads(resp.read().decode("utf-8"))
        return data["choices"][0]["message"]["content"]
    except error.HTTPError as e:
        print("HTTP 错误：", e.code, e.read().decode("utf-8")[:200])
        raise
```

**验收**：
- [ ] 能成功调通一次，拿到返回
- [ ] 能说清 `messages` 里 `role` 有哪几种
- [ ] 能说清 `temperature` 调高调低的区别

> ⚠️ **安全红线**：API Key 绝对不能写进代码、不能提交到 GitHub。这是 FDE 的底线。

## Day 44 · 让模型输出"能用"的格式

**问题**：模型默认输出一段自然语言，你没法程序化处理。

**任务**：用"结构化输出"约束它。

**提示词模板**（写进 `translate.py`）：

```
你是影视字幕翻译。把下面的字幕翻译成英文。

要求：
1. 只输出 JSON，不要任何解释
2. 格式：{"translations": [{"index": "1", "text": "..."}]}
3. 术语表里的词必须按术语表翻译
4. 保持口语，不要书面化

术语表：
{glossary}

待翻译：
{items}
```

**任务**：
1. 把字幕条目拼成 JSON 传进去
2. 解析返回，去掉可能的 ```json 包裹
3. 如果解析失败，**重试一次**，还失败就报错并记录原文

**验收**：
- [ ] 连续跑 5 次，至少 4 次能解析成功
- [ ] 解析失败时有清晰错误信息（保存原始返回）
- [ ] 能说清"为什么要它只输出 JSON"

## Day 45 · 术语一致性（这是你的行业壁垒）

**问题**：模型每次翻译可能把同一个角色名翻成不同版本。

**任务**：做一个**术语表机制**。

`glossary.json`：

```json
{
  "悟空": "Wukong",
  "师父": "Master",
  "金箍棒": "Golden Cudgel"
}
```

**要求**：
1. 翻译前把术语表塞进提示词
2. 翻译后**程序化检查**：术语表里的词，译文里是否按要求出现
3. 不符合的条目，标成 `terminology_mismatch`，进问题清单

> **关键洞察**：不要指望模型永远守规矩。**用代码做二次校验**——这就是"AI + 规则"的混合系统，也是 FDE 做企业项目的标准形态。

**验收**：
- [ ] 术语表生效
- [ ] 有二次校验
- [ ] 能说清"为什么不只靠提示词"

## Day 47 · 失败模式与兜底

**任务**：给 AI 调用加四层保护：

| 失败 | 兜底 |
|---|---|
| 网络超时 | 重试 3 次，间隔递增 |
| 限流（429） | 等待后重试 |
| 返回格式错 | 重试一次，仍错则跳过并记录 |
| 内容被拒 | 记录原文，人工处理 |

**验收**：
- [ ] 四种情况都有处理
- [ ] 失败的条目不会静默丢失（一定出现在日志或报告里）
- [ ] 能说清"静默失败为什么最可怕"

## Day 48 · 给 AI 部分写测试（用假数据）

**问题**：测试不能真的调 API（慢、花钱、不稳定）。

**学**：**Mock（打桩）**——用一个假函数替代真 API。

```python
def fake_call_llm(messages):
    return '{"translations": [{"index": "1", "text": "Don\'t look back"}]}'


def test_translate_parse(monkeypatch):
    import subtitle_qc.translate as t
    monkeypatch.setattr(t, "call_llm", fake_call_llm)
    result = t.translate_items([...], {})
    assert result[0]["text"] == "Don't look back"
```

**验收**：
- [ ] 测试不真的联网
- [ ] 覆盖"正常返回"和"格式错返回"
- [ ] 能说清"mock 是什么、为什么必须用"

# W9 · 第 9 周：交付（这是 FDE 的核心动作）

## Day 56 · 写交付四件套

**四份文档，缺一不可**：

| 文件 | 内容 | 为什么 |
|---|---|---|
| `README.md` | 5 分钟能跑起来 | 别人愿意用 |
| `ARCHITECTURE.md` | 一张架构图 + 数据流说明 | 别人能理解 |
| `RUNBOOK.md` | 启动/重启/回滚/查日志/找谁 | 出事能处理 |
| `LIMITATIONS.md` | 至少 5 条"它会在哪坏" | **最能建立信任** |

**验收**：
- [ ] 四份都有
- [ ] 找一个不懂的人照 README 跑一遍，能跑通
- [ ] `LIMITATIONS.md` 里至少 5 条，且都是真的

> **反常识**：`LIMITATIONS.md` 写得越诚实，客户越信你。
> 因为"什么都行"的承诺，有经验的人一听就知道是假的。

## Day 57 · 画架构图

**任务**：用任意工具（draw.io / Excalidraw / 甚至纸笔拍照）画一张图，包含：

**验收**：
- [ ] 图能讲清数据流
- [ ] 标出了人工介入点

## Day 58 · 录 3 分钟演示视频

**脚本**（严格按时间）：

| 时间 | 内容 |
|---|---|
| 0:00–0:20 | 痛点：字幕交付前靠人眼查，错了要返工 |
| 0:20–0:40 | 一句话说清："给一份字幕，30 秒出一份报告" |
| 0:40–1:50 | **现场演示**：拿一个坏文件跑一遍，看报告 |
| 1:50–2:30 | **数字**：20 条样本，检出率 85%，误报 3 条 |
| 2:30–2:45 | **取舍**：为什么只报问题不自动改 |

**要求**：
- 不要念稿，用"讲给同事听"的语气
- 画面要能看清操作
- **加字幕**（你是做字幕的，这是你的专业度）

**验收**：
